# Practical native cTrader Cloud recovery decision, after PR263 — no permission change

**Purpose:** Separate normal broker-visible recovery from the narrowly defined in-flight order ambiguity. This document defines an operational design constraint, not an assertion of general impossibility and not a Cloud or trading activation. Original `MxmNativeRunFence` intentionally remains unchanged: Cloud is observation-only, new order rights remain NO-GO.

## Verified native capabilities and present implemented facts

Official documentation: cTrader Cloud instances run independently of the client and are isolated; `Positions.FindAll(label[,symbol])`, `History.FindAll(label)`, `HistoricalOrders.FindAll(label)` are available in Cloud. Positions and deals live in the broker account, not in the mobile app process. Cloud LocalStorage durability across a stopped/restarted instance remains undocumented/unsuitable as a pre-send atomic journal: already verified PR263; a historical-order list can **positively attribute** a broker-assigned order/deal but does not prove that an absent in-flight request will never fill. This is a conditional statement about the currently evidenced primitives, not a universal claim against alternative platform protocols.

## Four distinct incident classes

1. **Known broker-open position**: broker-assigned stable position ID is present in the complete currently observed account book. On any instance start, reconstruct only positive facts: account/broker identity, full owner-labelled and foreign account exposures, symbol, side, volume, SL/TP, margin, fees/conversion availability and mark freshness. Reject conflicting duplicate symbols/IDs, unprotected positions, missing stops or stale account marks. This lets the bot resume read-only state/risk accounting; where separately supported and proven safe it could continue **position-ID-targeted protective management**, not new exposure. Existing broker-side protective SL remains broker-side if the bot is offline. No assertion of at-least-once duplicate-safe close/modify requests.
2. **Verified broker historical transaction**: historical order + opening deal / closed trade correlated with broker ID and original known intent provide positive attribution. Use the observed account state to reconstruct actual remaining positions/cost entries; never reconstruct a phantom open position merely from signal intent. A complete historical HARD21 counter requires explicit proof of all relevant broker opening deals and week UTC coverage; currently completeness cannot be inferred from the API's empty result alone.
3. **Unknown in-flight request**: the native call may have reached the broker even if no new broker position, deal or historical order is visible *yet*. No blind resubmit, no duplicate new market order, no erroneous 'history empty -> no order'. Quarantine that original intent and any potentially dependent entry; reserve the worst permissible phantom margin/risk within the **ENTIRE** account, not just its symbol. With the current owner EUR200 / EUR80 ticket / EUR120 free reserve / EUR2 stop-risk and no durable original intent, worst-case phantom exposure can consume all surplus admission budget, so new opening exposure **cannot be safely assumed permitted**. Other activities may proceed: broker observation, authentic quote acquisition, causal signal computation, reporting and non-mutating account reconciliation. Once a broker-final original result is established, quarantine can be released based on positive/final proof, not a time delay alone.
4. **Ordinary uninterrupted acknowledged operation**: follow the existing single-robot sequencer, normal checked broker results and risk admission. This is different from a crash during send. Do not universally label ordinary operation ambiguous. However a Cloud cold start *without an atomically durable transmit boundary* cannot distinguish a clean earlier stop from a crashed in-flight request just by its lack of position or history; therefore the current entry Cloud gate is still required until a verifiable protocol or independently qualified bounded-risk alternative is implemented.

## Proportionate recovery lane decision

- **Observation/reconciliation lane**: ON in Cloud observation mode under current original protections. Recover and monitor all *positive* broker facts with original historical-order, opening-deal and cashflow inventories; maintain risk budget and identity conflicts. Do not open orders.
- **Known-position protection lane**: design permitted in principle for confirmed exact broker position IDs, after proving exact API semantics, fresh broker marks, absolute target SL, live session gating, concurrent account events, and no generation of new/opening exposure. Not deployed, not an authorization to close/modify with unknown request outcome.
- **Entry/new-risk lane**: OFF for Cloud until verified state continuity across send/ack (documented broker idempotency or authoritative finality with identity and consistency guarantee; or another explicitly qualified safe protocol). Never infer idempotency from client comment or label. Never silently re-arm after restart or solely after a fixed timer.
- **System-level scope**: isolate a potentially ambiguous intent to its original signal, but account-wide risk must pessimistically include all unresolved possible exposures; unambiguous read-only and risk-limiting work need not stop. New trades on *other* symbols are allowed only if a strict, verified account-wide worst-case proof remains admissible after phantom exposure. This permission is NOT currently proven or implemented at initial EUR200 capital, so it remains closed.
- **Evidence to change conclusion**: human Spotware/ Pepperstone guarantee specifying unique client key, definitive response lifetime, late fill/finality bounds, completeness, Cloud durable intent mechanism OR concrete validated alternative; then independent deterministic crash-at-send fault injection with actual native Cloud acceptance before exposing new order permission. No LIVE/DEMO order authorized by this document.

**Residual risk:** broker records may lag the request; Cloud restart may lose local intent; other account actors may change positions; a close/modify request can itself be ambiguous; delayed fill can consume reserve after an apparently clean scan. These are not erased by general cloud uptime claims. This architecture avoids treating one exceptional crash as a reason to halt non-exposure work, without pretending that today's entire Cloud trading product is safely restartable.

**Owner controls unchanged:** hard21 whole account, single continuous EUR200 initial capital, protected net cost/risk, zero Cloud activations and zero LIVE/DEMO orders until owner explicitly authorizes an operational deployment.

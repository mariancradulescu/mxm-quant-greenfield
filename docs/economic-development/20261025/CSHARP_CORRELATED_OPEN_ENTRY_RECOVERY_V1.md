## Actual recovery path

New future opening attempts persist a version2 account-scoped record BEFORE the existing fresh account/risk calculations and opening call. It contains an unpredictable per-attempt GUID, exact comment derived from it, label/symbol/direction/units/stop/pip/tick geometry, decision boundary, preparation/deadline UTC and all pre-existing broker position IDs. The same comment is passed to the actual SDK `ExecuteMarketOrder` overload. The existing READY sentinel/storage key and old entry/fill journals remain compatible; an old unresolved V1 attempt is never silently upgraded or cleared.

[Official ExecuteMarketOrder overload](https://help.ctrader.com/ctrader-algo/references/General/Robot/ExecuteMarketOrder/) supports an order comment, and [Position.Comment](https://help.ctrader.com/ctrader-algo/references/Trading/Positions/Position/Comment/) exposes that property. This API contract does not prove native roundtrip retention, truncation behavior, callback timing or crash durability for our package. A comment is correlation data, NOT a broker idempotency key.

At cold startup, before any trading callback subscription, inspect the checkpoint without overwriting it. Typed pending requires the original, already persisted account fill ledger: missing, freshly recreated, wrong-scope, corrupt or later-started measurement cannot clear pending. Exactly one OPEN broker position must carry the identical correlation comment. Its identity must be new relative to the saved pre-call IDs; label, symbol, direction and FULL requested volume must match; actual broker entry UTC must be no earlier than preparation and no later than the current UTC observation. Current pip/tick geometry must match, and the owned broker book/stop must pass the existing order-protection guard. Any extra new position, duplicate ID/comment or pending broker order blocks recovery.

The actual broker collection provides the observed position/comment/time/stop/geometry. Recovery uses the shared protection-only book validator; the original API acknowledgement remains lost/unknown. Ordinary returned-order reconciliation retains its separate actual success-result check. Persist and verify the confirmed protected-entry count BEFORE clearing pending to READY. A crash after the count but before READY repeats only positive reconciliation; the fill ledger counts that position once. A changed pending marker, callback poison or unacknowledged storage operation never permits admission in the current instance. A READY write may have reached disk even if its acknowledgement fails; its write is ordered only AFTER positive attribution and durable counting, never as an inference that the original call was absent.

Recovery itself submits, retries and closes ZERO orders. It releases only the old unresolved bookkeeping state after positive proof. Startup strategy/fence state remains cold; the old signal is not replayed. All later new intents still pass existing ownership, current equity/margin/stop-risk, book-identity, expiry and trading-authority gates. All geometry is fixed in the durable request before the slow save; volumes/geometry are rechecked afterward and the final complete broker ID set must still match before the one opening call. No additional durable write is inserted after the final risk/clock checks.

## Conservative boundaries retained

Empty book, missing/truncated/changed comment, closed/disappeared positions, partial/excess volume, wrong ownership/direction/symbol, pre-existing or ambiguous identity, time/geometry/stop mismatch, pending orders, journal loss, legacy pending and storage faults remain blocked. There is no history-based closed-order recovery, proof of a negative broker acknowledgement, total-storage-loss/rollback detection, broker idempotency, inter-instance mutex or complete crash guarantee. Recovery is automatic at startup for the identifiable OPEN-position case; this does not implement platform restart orchestration or live in-place recovery of an already halted Robot.

The single owning instance and unchanged storage domain remain prerequisites. Attribution also assumes that other account clients do not forge/copy this attempt tag or submit the same request outside this path; a broker comment is not cryptographic origin evidence. Native timestamp precision or comment retention may conservatively prevent recovery; no tolerance or ownership guessing is introduced to hide that limitation. No foreign position is closed or modified. A missing old fill journal is not recreated merely to release a typed pending request. A full old journal capacity or inconsistent entry identity keeps admission stopped.

Cloud/CLI real-time storage remain unqualified under the existing Desktop-only guard. The actual Robot still targets net6 with the same12 parameters, empty roster, DEMO=false, risk/strategy/cost defaults and LIVE prohibition. No new data provider, broker request/order, funding/reset, authority/App/checkpoint writer or scientific partition is changed. Robust after-cost edge, one continuous EUR200 qualification, effective HARD21 and full native operational reception remain open.

# Before-call checkpoint for unresolved native entry attempts

Baseline: canonical `2765efbf7792d1279c99002656198735bf741ff2`, after PR167–168. The tested UTC-seasonality configuration remains stopped at `REFERENCE_FRICTION_FAIL`; no parameter/roster/hour rescue or new economic trial is introduced. This phase addresses a concrete product recovery gap.

## Counterexample and resulting behavior

PR165's `MxmOrderProtection.Halted` is in memory. A newly constructed Robot has a fresh guard. If an entry call had an ambiguous outcome and the process restarted, neither that latch nor an unresolved before-call marker existed in native storage. A flat or apparently protected broker book cannot by itself establish whether the old request was rejected, filled then closed, or still unresolved. Restart must not silently restore normal entry admission on that basis.

`MxmEntryCheckpoint` now saves and reads back a unique PENDING attempt before any opening broker call. The marker includes schema, account-scope commitment, random attempt identity, symbol, direction and source bar boundary. It is a safety checkpoint, not a restored trading signal, financial ledger, broker request ID or broker idempotency guarantee. It never authorizes a replay.

At startup, only absence on first use or the exact READY value for this account scope may initialize the barrier. Any other value, including partial, corrupt, unknown-version or pending data, blocks startup without overwriting it. Startup also performs an explicit READY save/readback probe. No user parameter bypasses this barrier. The key is <=50 alphanumeric/space characters, scoped by the existing owner label, normalized broker name, account number and DEMO/LIVE identity; strategy, roster and timeframe changes cannot select a different key. A different broker/account identity or storage domain is a different scope; deletion/migration of storage is not detected by an external authority anchor.

The native adapter uses explicit `LocalStorageScope.Type`, with `Flush` on writes and `Reload` before reads, so the same algorithm/account can see its marker across local instance restarts. No new access rights are requested. All risk/margin/account snapshots follow the potentially slow before-call write. Immediately before calling the broker, the adapter rechecks the position fence and bar-intent expiry. A known local rejection before the call can clear the prepared marker; once the call is marked attempted, only the existing returned-result/book/stop reconciliation can complete it. An unsuccessful API result, even with no returned identity and an empty observed book, does not disarm the marker: this adapter has no separately proven durable negative acknowledgment. It therefore halts conservatively for reconciliation, including ordinary rejected calls, rather than infer that the request never reached the broker. This reduces availability until a trustworthy rejection/reconciliation route is qualified. An exception, unknown result, protection fault or inability to complete storage leaves admission halted. The marker is not cleared by Stop, a new instance, a changed strategy/roster or a successful defensive close.

## Failures and platform limits

Storage exceptions, failed readback and changed markers poison the barrier. cTrader can deliver LocalStorage failures through `OnException`, rather than throw at the call site: the adapter's handler irreversibly poisons both journal and admission, clears intents and stops. The storage wrappers check that poison after each API operation. A matching cached/memory echo cannot undo the fault. Callback recursion during stopping is suppressed.

Real-time persistence is currently allowed only on `EnvironmentType.Desktop`; other environments stop before subscriptions or orders. Current official Cloud LocalStorage documentation says values are run-local and Flush/Reload do not establish persistence. Backtests use an explicit fresh memory store, without reading or writing the real account marker. This is not Cloud activation, a new Cloud backend, CLI acceptance or proof that desktop persistence survives actual cTrader/OS/storage failures.

An unresolved marker stays conservatively blocked until separately trustworthy reconciliation exists. This change prevents silent restart bypass; it does **not** implement autonomous resolution of every unknown broker outcome. There is no automatic marker reset, guessed rejection, inferred fill, speculative close or repeated opening request. A single owning Robot and unchanged account/storage identity remain required. Type-scope read/compare/write is not an inter-instance mutex, atomic broker transaction, remote/multi-device durable journal, tamper-proof store or power-loss certificate. Actual platform behavior, storage error timing and crash reception still require native cTrader evidence. The existing returned-ID defensive closure policy is preserved.

## Verification

The shared C# fixture reproduces the old memory-only restart counterexample. It exercises missing/ready/pending/corrupt state, account identity separation, broker-name canonicalization, invalid clear-after-submission, storage read/write/drop faults, nonthrowing callback poison, changed-attempt refusal, successful reconciliation, unsuccessful-result/empty-book refusal to disarm, and a halt that cannot clear an unresolved marker.

Four fresh worker processes stage artificial states: prepared before broker call, simulated call made, halted after simulated call, and reconciled. The parent abruptly kills each worker after its durable file-store handshake; no finally/OnStop cleanup runs. Four additional new OS processes recover from those files. The three unresolved cases must remain blocked; only the reconciled READY case admits initialization. Fake-broker witness counts must never increase on recovery. The file test adapter flushes original bytes before atomic replacement; this is an artificial-process test on the CI filesystem, not cTrader LocalStorage or power-loss reception. All eight child processes are actual new OS processes, not reconstructed objects in parent memory.

Existing no-secret account CI compiles the actual `.algo`, executes the fixture, verifies adapter ordering/fault wiring and retains the original synthetic JSON proof as a CI artifact. No actual orders, market-data reads, economic simulations or scientific trials are performed by this fixture. Existing merge-triggered protected chronology/account/lifecycle workflows may rerun their unchanged DEVELOPMENT programs; those repeats are technical regressions, not independent economic evidence or new research identities.

The account remains the real continuously shared broker account; no capital epoch or EUR200 balance reset is added. Robust after-cost economic advantage, effective HARD21 and complete native cTrader operational acceptance remain open. Existing authority/checkpoints, C033, canonical V2 and DEVELOPMENT / CONFIRMATION / PROTECTED separations remain unchanged.
